# Контекст проекта

Проект предназначен для изучения и практики автоматизированного тестирования REST API на Java.

Основные цели:
- Разрабатывать качественные и поддерживаемые API-автотесты.
- Практиковаться в использовании современных инструментов автоматизации.
- Изучать лучшие практики Java и тестирования API.
- Постепенно улучшать архитектуру тестового фреймворка.
- Готовиться к техническим собеседованиям на позицию QA Automation Engineer.

## Технологический стек

- Java
- REST Assured — тестирование REST API
- TestNG — организация и запуск тестов
- AssertJ — проверки результатов
- Jackson — сериализация и десериализация JSON
- Lombok — сокращение boilerplate-кода
- Maven — сборка проекта и управление зависимостями
- IntelliJ IDEA — основная среда разработки

Перед использованием новых библиотек проверяй существующие зависимости проекта. Не добавляй зависимости без необходимости.

## Принципы проекта

- Простой и понятный код важнее сложной архитектуры.
- Следуй существующей структуре проекта.
- Не создавай дополнительные классы и абстракции без реальной необходимости.
- Избегай дублирования кода.
- Тесты должны быть независимыми и воспроизводимыми.
- Используй понятные названия методов, переменных и классов.
- Не усложняй решения ради применения паттернов проектирования.
- Не изменяй существующую архитектуру без предварительного согласования.

## Правила написания API-автотестов

- Используй REST Assured для HTTP-запросов.
- Используй TestNG для организации тестов.
- Предпочитай AssertJ для проверок, когда это удобно.
- Используй DTO для работы со сложными JSON-ответами.
- Используй Jackson для сериализации и десериализации.
- Используй Lombok для сокращения boilerplate-кода, если он уже подключён.
- Придерживайся подхода Arrange / Act / Assert.
- Проверяй HTTP status code.
- Проверяй значения важных полей response body.
- При необходимости проверяй JSON schema, headers и response time.
- Покрывай позитивные, негативные и граничные сценарии.
- Проверяй поведение API при некорректных параметрах.
- Учитывай авторизацию, права доступа и обработку ошибок.
- Не используй Thread.sleep() для ожидания.
- Не делай тесты зависимыми от порядка выполнения.
- Используй DataProvider для параметризации, когда это действительно полезно.
- Не хардкодь секреты, токены и пароли.
- Не предполагай, что API соответствует требованиям, без проверки документации или фактического поведения.

## REST Assured

Предпочитай читаемый стиль Given / When / Then.

Пример:

```java
@Test
public void shouldGetUserById() {
    Response response = given()
            .when()
            .get("/users/2");

    assertThat(response.statusCode()).isEqualTo(200);

    UserResponse userResponse = response.as(UserResponse.class);

    assertThat(userResponse.getData().getId()).isEqualTo(2);
}
```

Не добавляй дополнительные уровни абстракции для простых тестов.

## DTO и модели

- Используй понятные названия DTO.
- Применяй @JsonProperty, если JSON-поле отличается от Java-поля.
- Применяй @JsonIgnoreProperties(ignoreUnknown = true) только тогда, когда дополнительные поля допустимы по контракту API.
- Не используй DTO для каждого простого ответа, если это неоправданно.
- Сравнивай объекты через AssertJ usingRecursiveComparison(), когда это удобно и логически корректно.
- Учитывай вложенную структуру JSON при десериализации.

# Запуск и проверки

## Окружение

Для работы необходимы:

- Установленный JDK совместимой с проектом версии.
- Maven или Maven Wrapper.
- IntelliJ IDEA.
- Доступ к тестируемому API.
- Необходимые переменные окружения для авторизации, если API их требует.

Не предполагай конкретную версию Java без проверки pom.xml.

## Сборка

Если в проекте используется Maven Wrapper:

```bash
./mvnw clean compile
```

Если Maven Wrapper отсутствует:

```bash
mvn clean compile
```

## Запуск тестов

Запуск всех тестов:

```bash
mvn test
```

Запуск конкретного тестового класса:

```bash
mvn -Dtest=UserApiTest test
```

Запуск конкретного метода:

```bash
mvn -Dtest=UserApiTest#shouldGetUserById test
```

Если доступен Maven Wrapper, используй ./mvnw вместо mvn.

Перед запуском проверяй реальные имена классов, настройки Surefire и конфигурацию проекта.

## Правила проверок

- Не запускай тесты без моего запроса.
- После изменения кода сообщай, какие проверки рекомендуется выполнить.
- Не утверждай, что тесты прошли успешно, если они не запускались.
- Если тесты запускались, сообщай результат.
- При падении тестов указывай причину, если она установлена.
- Не исправляй ожидаемые значения только ради прохождения тестов.
- При проблемах с окружением отделяй их от дефектов тестируемого API.
